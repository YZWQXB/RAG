# 检索质量改进：多轮指代消解 + 评测闭环

> 版本：v1.2 开发中
> 日期：2026-11-15
> 起因：`app/modules/retrieval/rewrite.py` 里写着「首期刻意不做 LLM 改写…等评测集有数据后再决定」，
> 而评测集只有 21 条、CI 也不跑。这两件事互为前提：没有评测就不敢做改写，不做改写评测也没有意义。

## 一、为什么要做这两件事

面试官问 RAG 项目通常会追三层，前两层已经扎实，后两层是空的：

| 追问 | 现状 |
|---|---|
| 多租户怎么隔离、入库怎么保证不丢 | 强（RLS、outbox、幂等、限流） |
| **你怎么证明改完没变差** | 弱：有 `scripts/eval.py`，但只 21 条、CI 不跑、没有上下文级指标 |
| **多轮能不能真聊起来** | 弱：检索用裸 query，「它有什么限制」必然落空 |

## 二、多轮指代消解

### 问题

`_prepare` 把历史塞进了生成提示词，但**检索层拿到的是裸 query**。
「它」「那…呢」这类追问在分块文本里根本不存在，召回必然为 0——不是阈值问题，是查询信息不足。

### 设计：三层闸门 + 「失败才改写」的时机策略

**第一版设计是无条件改写，实测被否掉了**：上游首字延迟约 6 秒，3 秒超时必然放弃，
日志里连续两条 `rewrite_timeout`。等于给每次提问都加了 6 秒却什么都没换到。

改为**先检索、失败才改写**：

```
按原句检索（约 200ms）
  ├── 可作答 → 直接生成            （零额外延迟、零额外 token）
  └── 不可作答 → 改写（≤10s）→ 重试检索
                 ├── 可作答 → 用改写结果生成，前端提示"已结合上文改写检索"
                 └── 仍不可作答 → 原样拒答（说明确实没有资料，不是表述问题）
```

| 闸门 | 规则 | 理由 |
|---|---|---|
| 时机 | 只有「按原句检索不到依据」才改写 | 常规提问零成本；本来就是拒答的追问，多等几秒换一个能答的结果是划算的 |
| 门控 | 有历史 **且** 问句 ≤ `QUERY_REWRITE_MAX_CHARS`（15 字）**且** 含指代词（它/这个/该/那…呢/继续/详细） | 长句自带主语，改了反而可能引入偏差；首轮没有依据 |
| 超时 | `QUERY_REWRITE_TIMEOUT_SECONDS`（10 秒） | 失败路径上的等待可以给得宽；早期用 3 秒，实测必然超时 |
| 缓存 | `rw:{sha256(问句+上下文)}`，TTL 1 小时，键不含明文 | 多轮反复追问不重复烧 token；Redis 里不留用户原文 |

另外支持 `QUERY_REWRITE_MODEL` 指定小模型：几十 token 的改写任务不必占用主力模型。

**兜底原则：宁可检索不到，不能检索错。** 上游报错、超时、模型输出「抱歉我无法…」、
输出过长或与原句等价，一律退回原句。

### 关键实现点

- `rewrite.py::maybe_rewrite()` 是唯一入口，返回 `(检索用查询, 是否真的改了)`
- 顺序不能反：**先改写，再编码**。被 embedding 的必须是改写后的句子，否则向量与查询对不上
- 离线模式（`LLM_PROVIDER=fake`）直接跳过：假模型不会改写，调用它只会白等三秒
- `citations` 事件新增 `rewritten_query` 字段，前端显示「已结合上文改写检索：xxx」，
  让用户知道检索实际用的是什么
- 指标：`rag_query_rewrite_total{result}`（applied / rejected / timeout / failed）

## 三、评测闭环

### 3.1 修掉一个口径不一致的 bug

`scripts/eval.py` 里的拒答判定是 `top_dense_score < threshold`，
而线上用的是 `answerable(top_dense, top_sparse)` 双通道判定。
**评测结论与线上行为不一致，等于在用错的尺子量。** 已统一为线上口径。

### 3.2 指标

| 指标 | 定义 | 为什么需要 |
|---|---|---|
| recall@5 | 前 5 条候选命中标注块的比例 | 召回层能力 |
| MRR | 首个命中排名的倒数 | 排序质量 |
| **context_recall** | 标注块进入**最终上下文**的比例 | 候选命中但没进上下文，等于白搭——这是 recall@5 看不出来的 |
| no_answer_accuracy | 无答案问题被正确拒答的比例 | 防硬答 |
| p50 / p95 | 单次检索耗时 | 改动不能以延迟为代价 |

### 3.3 语料与数据集

- 语料从 3 篇文档扩到 6 篇（新增 `it_security.md`、`travel_expense.md`、`onboarding.md`），
  覆盖互不相关的主题——否则「召回不到」和「召回到错主题」区分不开
- 评测集 21 → 69 条：fact 38 / compare 15 / cross 6 / no_answer 10
- **标注解析不到分块时直接报错退出**，不再静默跳过：静默跳过会让指标凭空变好

### 3.4 门禁

- `scripts.eval --check`：任一指标相对基线退化超过 0.02 即非零退出
- `scripts.eval_rewrite --check`：改写必须带来正收益（lift > 0），门控准确率 ≥ 0.9
- 自动生成 `docs/reports/eval-latest.md` 与 `eval-rewrite-latest.md`，CI 归档为 artifact
- 日常跑数不受门禁影响，只有 `--check` 才阻断

### 3.5 改写效果怎么测（重要取舍）

`eval_rewrite` 用**人工标注的改写结果**替换模型输出，测的是「改写的收益上限」。
这样把「改写器好不好」和「改写有没有用」拆开：如果连金标准改写都提不了分，
就该关掉这个功能，而不是去调模型。真实改写质量属于线上灰度指标。

## 三点五、实测数据（2026-11-15）

### 检索质量（`docs/reports/eval-latest.md`）

语料 6 篇 / 23 块，评测集 69 条，`embedding=local(bge-m3)`：

| 指标 | 值 |
|---|---|
| recall@5 | 1.0 |
| MRR | 0.9703 |
| context_recall | 1.0 |
| no_answer 准确率 | 0.8（10 条硬负例中 2 条误答） |
| 检索耗时 p50 / p95 | 196ms / 215ms |

两条误答（`火星基地的差旅报销标准`、`公司有没有员工持股计划`）都是**主题相邻的硬负例**：
前者命中「差旅报销」整章，后者命中「员工手册」。这类问题靠提高阈值只会误伤真问题，
真正的解法是答案级校验（claim 是否被引用块支持），属于下一轮。

### 多轮改写（`docs/reports/eval-rewrite-latest.md`）

| 指标 | 值 |
|---|---|
| 裸追问 recall@5 | 0.8462 |
| 改写后 recall@5 | 1.0 |
| lift | +0.1538 |
| 门控准确率 | 1.0（13/13） |

收益集中在**完全没有实词重合**的追问（「这个多久要换」「这个怎么处理」），
这两条裸召回为 0；而「那主要部件呢」这类含实词的追问，裸召回本来就过线——
说明门控「只在需要时才改写」是必要的，否则一半的改写是白花的。

### 实机链路（真实 bge-m3 + 星火）

```
[TCP 三次握手的过程]      12.2s  改写=None                      引用=6
[那它和四次握手有什么区别] 19.1s  改写=TCP 三次握手过程与四次挥手的过程区别是什么  引用=6
```

追问原本会因「资料未涵盖」被拒，改写后正常作答；日志 `rewrite_applied from_len=12 to_len=23`。
